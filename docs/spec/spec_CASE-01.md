# spec_CASE-01 — риск-правила перед одобрением заявки

> Спека по `docs/intent/intent_CASE-01.md` и материалам кейса `docs/sources/CASE-01.md`.
> Все данные синтетические. Числа — только из материалов кейса (источник указан у каждого).

## 1. Входит / не входит

**Входит**
- Проверка заявки набором риск-правил П-1…П-5 до одобрения; исход «прошла / не прошла / эскалировано / техническая ошибка» с перечнем сработавших правил (`docs/sources/CASE-01.md:12`).
- Передача заявки риск-менеджеру при двух и более срабатываниях (`docs/sources/CASE-01.md:29`, `docs/sources/CASE-01.md:86`).
- Данные для карточки эскалации (`docs/sources/CASE-01.md:104`).
- Поведение при нераспознанном типе ТС и недоступности сервиса активных займов.

**Не входит** (интент, `docs/intent/intent_CASE-01.md:30`)
- Существующий расчёт решения по LTV (approve / review / reject).
- Хранение заявок и БД.
- Frontend.
- Seed-данные.
- Интеграция и доступность сервиса клиентов (вопрос доступности — только поведение проверки при его недоступности).
- UI карточки эскалации.
- Ручные исключения риск-менеджера (Q9; `docs/sources/CASE-01.md:98`).
- Переработка лимита суммы по типам ТС в действующей валидации — вынесено в Open questions (OQ-2).

## 2. Требования

### REQ-CASE-01-01 — вердикт риск-проверки
Проверка отдаёт один из четырёх исходов: «прошла» или «не прошла» — с перечнем сработавших правил; «эскалировано» (REQ-CASE-01-07); «техническая ошибка» (REQ-CASE-01-11). Источник: `docs/sources/CASE-01.md:12`, `docs/sources/CASE-01.md:13`.

- **AC-CASE-01-01** — Given заявка без срабатываний правил (A-1001: легковой, 1 800 000 ₽, 1 активный займ, `docs/sources/CASE-01.md:36`), When проверка выполнена, Then вердикт «прошла», перечень сработавших правил пуст. → REQ-CASE-01-01
- **AC-CASE-01-02** — Given заявка, по которой сработало ровно одно правило, When проверка выполнена, Then вердикт «не прошла», в перечне все сработавшие правила (полнота — REQ-CASE-01-08). → REQ-CASE-01-01

### REQ-CASE-01-02 — последовательная проверка
Все правила применяются к заявке независимо от того, сработало ли предыдущее. Источник: регламент п. 2.1, `docs/sources/CASE-01.md:77`.

- **AC-CASE-01-03** — **ждёт решения OQ-3** (возраст залога A-1004 больше 20 лет — перехват действующей валидацией): Given заявка A-1004 (`docs/sources/CASE-01.md:42`: коммерческий, 2003, 400 000 ₽, 3 активных), When проверка выполнена, Then в перечне и П-2, и П-3, хотя П-2 уже сработал, и итог — эскалация (ожидание кейса, `docs/sources/CASE-01.md:49`). → REQ-CASE-01-02
- **AC-CASE-01-04** — Given заявка, по которой сработало П-1, When проверка выполнена, Then П-2, П-3 и П-4 всё равно применяются. → REQ-CASE-01-02

### REQ-CASE-01-03 — П-1: лимит суммы по типу ТС
Максимальная сумма: легковой — 2 000 000 ₽, коммерческий — 3 000 000 ₽, мотоцикл — 500 000 ₽. Источник: `docs/sources/CASE-01.md:25`, регламент п. 2.3 `docs/sources/CASE-01.md:81`. Граница включительная (интент Q3, `docs/intent/intent_CASE-01.md:12`).

- **AC-CASE-01-05** — Given легковой ТС и сумма ровно 2 000 000 ₽ (A-1002, `docs/sources/CASE-01.md:38`), When проверка выполнена, Then П-1 не срабатывает. → REQ-CASE-01-03
- **AC-CASE-01-06** — Given легковой ТС и сумма 2 000 001 ₽, When проверка выполнена, Then П-1 срабатывает. → REQ-CASE-01-03
- **AC-CASE-01-07** — Given коммерческий ТС и сумма ровно 3 000 000 ₽, When проверка выполнена, Then П-1 не срабатывает; Given коммерческий ТС и сумма 3 000 001 ₽, When проверка выполнена, Then П-1 срабатывает. → REQ-CASE-01-03
- **AC-CASE-01-08** — Given мотоцикл и сумма ровно 500 000 ₽, When проверка выполнена, Then П-1 не срабатывает; Given мотоцикл и сумма 600 000 ₽ (A-1003, `docs/sources/CASE-01.md:40`), When проверка выполнена, Then П-1 срабатывает. → REQ-CASE-01-03
- **AC-CASE-01-09** — Given пустой тип ТС или значение не из списка, When проверка выполнена, Then техническая ошибка по REQ-CASE-01-11: П-1 не применяется. → REQ-CASE-01-03

### REQ-CASE-01-04 — П-2: лимит активных займов
У клиента не может быть больше лимита активных займов; заявка сверх лимита не проходит по П-2. Источник: правило П-2 `docs/sources/CASE-01.md:26`. **Значение лимита не задано**: регламент — не более двух (`docs/sources/CASE-01.md:84`), тикет — не больше трёх (`docs/sources/CASE-01.md:71`); OQ-1, решает риск-менеджер. Граница включительная: активных займов ровно лимит → проходит, лимит+1 → не проходит (интент Q3, `docs/intent/intent_CASE-01.md:12`).

- **AC-CASE-01-10** — **ждёт решения OQ-1**: Given число активных займов равно лимиту N, When проверка выполнена, Then П-2 не срабатывает. → REQ-CASE-01-04
- **AC-CASE-01-11** — **ждёт решения OQ-1**: Given число активных займов N+1, When проверка выполнена, Then П-2 срабатывает (третья заявка отклоняется при N=2, `docs/sources/CASE-01.md:26`). → REQ-CASE-01-04
- **AC-CASE-01-12** — Given данных по активным займам нет (сервис недоступен), When проверка выполнена, Then П-2 не проверяется — по REQ-CASE-01-12. → REQ-CASE-01-04

### REQ-CASE-01-05 — П-3: возраст залога
Возраст залога больше 20 лет — срабатывание П-3; 20 лет и меньше — проходит. Источник: `docs/sources/CASE-01.md:27`. 20 лет — из `docs/sources/CASE-01.md:27` и совпадает с действующей валидацией `backend/src/Domain/ApplicationValidator.php:39` (см. OQ-3).

- **AC-CASE-01-13** — Given год расчёта 2026 и год выпуска 2006 (ровно 20 лет), When проверка выполнена, Then П-3 не срабатывает. → REQ-CASE-01-05
- **AC-CASE-01-14** — **ждёт решения OQ-3** (действующая валидация отсекает такую заявку раньше риск-проверки): Given год расчёта 2026 и год выпуска 2005 (21 год) или старше, When проверка выполнена, Then П-3 срабатывает. → REQ-CASE-01-05
- **AC-CASE-01-15** — **ждёт решения OQ-3**: Given заявка с возрастом залога больше 20 лет, When проверка выполнена, Then достигает ли заявка П-3 — не определено (перехват действующей валидацией, `backend/src/Domain/ApplicationValidator.php:39`). → REQ-CASE-01-05

### REQ-CASE-01-06 — П-4: минимальная сумма
Сумма ниже 50 000 ₽ — обычное риск-правило: вердикт «не прошла» с причиной, попадает в перечень и в подсчёт для П-5. Источник: минимум 50 000 ₽ — `docs/sources/CASE-01.md:28`, совпадает с `backend/config/rules.php:28`; трактовка «обычное правило, а не техническая ошибка» — интент Q4, `docs/intent/intent_CASE-01.md:14`.

- **AC-CASE-01-16** — Given сумма ровно 50 000 ₽, When проверка выполнена, Then П-4 не срабатывает: ровно 50 000 ₽ — не «ниже» минимума (граница из слова «ниже» в П-4, `docs/sources/CASE-01.md:28`). → REQ-CASE-01-06
- **AC-CASE-01-17** — **ждёт решения OQ-3** (действующая валидация отсекает такую заявку раньше риск-проверки): Given сумма 49 999 ₽ и ниже (A-1005, 40 000 ₽, `docs/sources/CASE-01.md:44`), When проверка выполнена, Then П-4 срабатывает. → REQ-CASE-01-06
- **AC-CASE-01-18** — **ждёт решения OQ-3** (действующая валидация отсекает такую заявку раньше риск-проверки): Given сработали П-4 и ещё одно правило, When выполняется подсчёт для П-5, Then П-4 учтён в подсчёте и исход — «эскалировано». → REQ-CASE-01-06
- **AC-CASE-01-19** — **ждёт решения OQ-3**: Given сумма ниже 50 000 ₽, When проверка выполнена, Then достигает ли заявка П-4 — не определено (перехват валидацией, `backend/src/Domain/ApplicationValidator.php:54`). → REQ-CASE-01-06

### REQ-CASE-01-07 — П-5: эскалация при двух и более срабатываниях
При двух и более сработавших правилах исход — «эскалировано», а не отказ: заявка остаётся в работе, решение принимает человек в течение суток. Источник: `docs/sources/CASE-01.md:29`, регламент п. 2.7 `docs/sources/CASE-01.md:86`; «эскалация — не отказ», сутки — `docs/sources/CASE-01.md:103`.

- **AC-CASE-01-20** — Given ровно одно срабатывание, When проверка выполнена, Then вердикт «не прошла», без эскалации. → REQ-CASE-01-07
- **AC-CASE-01-21** — **ждёт решения OQ-3** (возраст залога A-1004 больше 20 лет — перехват действующей валидацией): Given два срабатывания (A-1004: П-2 и П-3, `docs/sources/CASE-01.md:49`), When проверка выполнена, Then исход «эскалировано», заявка не отказана. → REQ-CASE-01-07
- **AC-CASE-01-22** — Given три и более срабатываний, When проверка выполнена, Then исход «эскалировано». → REQ-CASE-01-07

### REQ-CASE-01-08 — полный перечень причин
Перечень причин полный, сокращать нельзя — и в отказе, и в карточке эскалации. Источник: регламент п. 2.7 `docs/sources/CASE-01.md:86`; интент Q2, `docs/intent/intent_CASE-01.md:16`. Противоречит тикету («одна, самая первая причина», `docs/sources/CASE-01.md:72`) — приоритет у регламента, как в интенте.

- **AC-CASE-01-23** — Given два сработавших правила, When формируется перечень причин (в отказе или в карточке эскалации), Then в перечне обе причины, а не одна первая. → REQ-CASE-01-08

### REQ-CASE-01-09 — порядок правил в перечне
Порядок — по фактическому срабатыванию при проверке заявки, не по номеру правила и не по тяжести. Источник: интент Q7, `docs/intent/intent_CASE-01.md:17`.

- **AC-CASE-01-24** — **ждёт решения OQ-5** (порядок выполнения проверок П-1…П-4 не задан ни в кейсе, ни в интенте): Given заявка, где П-3 срабатывает раньше П-1, When формируется перечень причин, Then П-3 идёт в перечне перед П-1. → REQ-CASE-01-09

### REQ-CASE-01-10 — состав карточки эскалации
В карточку эскалации попадают: id заявки, перечень сработавших правил с их значениями, данные заявки без ПДн. Источник: `docs/sources/CASE-01.md:104`.

- **AC-CASE-01-25** — **ждёт решения OQ-3** (возраст залога A-1004 больше 20 лет — перехват действующей валидацией): Given заявка A-1004 с двумя сработавшими правилами, When формируется карточка эскалации, Then в карточке есть id `A-1004`, сработавшие правила с их значениями (П-2: 3 активных, П-3: 2003 год) и данные заявки; полей с ПДн нет. → REQ-CASE-01-10

### REQ-CASE-01-11 — нераспознанный тип ТС
Пустой тип ТС или значение не из списка — техническая ошибка: заявка проверку не проходит, П-1 не применяется. Источник: интент Q6, `docs/intent/intent_CASE-01.md:19`; `docs/sources/CASE-01.md:56`.

- **AC-CASE-01-26** — Given пустой `vehicle_type`, When проверка выполнена, Then техническая ошибка: П-1 не применяется, вердикта «прошла» нет. → REQ-CASE-01-11
- **AC-CASE-01-27** — Given `vehicle_type: «квадроцикл»` (не из списка), When проверка выполнена, Then как в AC-CASE-01-26: техническая ошибка, П-1 не применяется. → REQ-CASE-01-11
- **AC-CASE-01-28** — **ждёт решения OQ-4**: Given техническая ошибка по нераспознанному типу ТС (`docs/sources/CASE-01.md:56`), When выполняется подсчёт для П-5, Then попадает ли ошибка в подсчёт — не определено. → REQ-CASE-01-11

### REQ-CASE-01-12 — сервис активных займов недоступен
Если сервис клиентов недоступен и данных по активным займам нет, П-2 не проверяется, заявка идёт по остальным правилам, факт недоступности логируется. Источник: интент Q8, `docs/intent/intent_CASE-01.md:20`; вопрос — `docs/sources/CASE-01.md:60`.

- **AC-CASE-01-29** — Given сервис активных займов недоступен, When проверка выполнена, Then П-2 не проверяется, остальные правила применяются, в логе есть факт недоступности. → REQ-CASE-01-12
- **AC-CASE-01-30** — Given сервис недоступен и других срабатываний нет, When проверка выполнена, Then вердикт «прошла». → REQ-CASE-01-12
