# spec_MILEAGE — пробег в решении по заявке

ID задачи: MILEAGE. Источник замысла: `docs/intent/intent_MILEAGE.md`. Сверка перед реализацией: `docs/plan/plan_MILEAGE.md`.

## Входит

- Правило: пробег ≤ 400 000 км (включительно) — правило пробега не срабатывает, итоговое решение определяется LTV.
- Правило: пробег > 400 000 км — итоговое решение `review`.
- Приоритет правил: если одновременно `mileage > 400 000` и `LTV > review_max` (порог reject по LTV), побеждает `reject`.
- Порог пробега для правила решения — 400 000 км.
- Существующая проверка пробега в `ApplicationValidator` (диапазон `0..max_mileage_km`) и существующие пороги LTV остаются без изменений.

## Не входит

- Валидация пробега (включая существующий `max_mileage_km = 500 000` и текст ошибки валидации).
- Расчёт LTV.
- Хранение, БД, frontend, seed-данные.
- Расчёт лимита суммы и лимит LTV по возрасту авто (задача LOAN-12).
- Feature-тесты.
- Реакция UI на `review` из-за пробега.

Источник: `docs/intent/intent_MILEAGE.md`, раздел «Не входит» (ответ в интервью Q4).

## Требования

### REQ-MILEAGE-01 — порог пробега для решения

Источник: `docs/intent/intent_MILEAGE.md` (Constraints: «Граница — 400 000 км»; ответ в интервью Q1, Q2).

Порог пробега для правила решения равен **400 000 км**.

### REQ-MILEAGE-02 — пробег ≤ 400 000: правило не срабатывает

Источник: `docs/intent/intent_MILEAGE.md` (Constraints: «Пробег ≤ 400 000 км (включительно) — правило не срабатывает, решение определяется LTV»; ответ в интервью Q1).

Если пробег ≤ 400 000 км, правило пробега не влияет на итоговое решение: решение определяется только LTV по существующим порогам `ltv.approve_max` и `ltv.review_max`.

### REQ-MILEAGE-03 — пробег > 400 000: решение review

Источник: `docs/intent/intent_MILEAGE.md` (Constraints: «Пробег > 400 000 км — решение review»; ответ в интервью Q1; исходная формулировка задачи в `docs/intent/grill_MILEAGE.md`).

Если пробег > 400 000 км, итоговое решение по заявке — `review` при условии, что LTV сам по себе не даёт `reject` (см. REQ-MILEAGE-04).

### REQ-MILEAGE-04 — приоритет: reject по LTV важнее review по пробегу

Источник: `docs/intent/intent_MILEAGE.md` (Constraints: «Приоритет: если одновременно пробег > 400 000 км и LTV > порога reject, побеждает reject»; ответ в интервью Q2).

Если одновременно выполнены оба условия: `mileage > 400 000` и `LTV > ltv.review_max`, итоговое решение — `reject` (правило пробега не понижает `reject` до `review`).

## Критерии приёмки

### AC-MILEAGE-01 — пробег 399 999 при низком LTV → approve

Ссылка: REQ-MILEAGE-01, REQ-MILEAGE-02.

- **Given** LTV = 30.0 (ниже `ltv.approve_max = 60.0`) и пробег = 399 999 км.
- **When** вызывается расчёт решения по заявке.
- **Then** итоговое решение — `approve`.

### AC-MILEAGE-02 — пробег 400 000 на границе при низком LTV → approve

Ссылка: REQ-MILEAGE-01, REQ-MILEAGE-02.

- **Given** LTV = 30.0 и пробег = 400 000 км (ровно на пороге).
- **When** вызывается расчёт решения по заявке.
- **Then** итоговое решение — `approve` (граница включительно, правило пробега не срабатывает).

### AC-MILEAGE-03 — пробег 400 001 при низком LTV → review

Ссылка: REQ-MILEAGE-01, REQ-MILEAGE-03.

- **Given** LTV = 30.0 и пробег = 400 001 км (сразу за порогом).
- **When** вызывается расчёт решения по заявке.
- **Then** итоговое решение — `review` (правило пробега перекрывает approve при низком LTV).

### AC-MILEAGE-04 — пробег > 400 000 при LTV > review_max → reject

Ссылка: REQ-MILEAGE-01, REQ-MILEAGE-04.

- **Given** LTV = 120.0 (выше `ltv.review_max = 85.0`) и пробег = 400 001 км.
- **When** вызывается расчёт решения по заявке.
- **Then** итоговое решение — `reject` (reject по LTV важнее review по пробегу).

### AC-MILEAGE-05 — пробег 0 (валидный, ниже порога) при низком LTV → approve

Ссылка: REQ-MILEAGE-02.

- **Given** валидный payload с `mileage = 0` и LTV ниже `ltv.approve_max`.
- **When** вызывается `AssessmentService::assess()`.
- **Then** итоговое решение — `approve` (0 ≤ 400 000, правило пробега не срабатывает).

### AC-MILEAGE-06 — пробег ≤ 400 000 при LTV в серой зоне → review (определяет LTV)

Ссылка: REQ-MILEAGE-02.

- **Given** LTV = 72.3 (в диапазоне `ltv.approve_max < LTV <= ltv.review_max`) и пробег = 400 000 км (ровно на границе порога).
- **When** вызывается расчёт решения по заявке.
- **Then** итоговое решение — `review` (правило пробега не сработало, решение определяет LTV).

### AC-MILEAGE-07 — пробег ≤ 400 000 при LTV выше review_max → reject (определяет LTV)

Ссылка: REQ-MILEAGE-02.

- **Given** LTV = 120.0 (выше `ltv.review_max = 85.0`) и пробег = 399 999 км.
- **When** вызывается расчёт решения по заявке.
- **Then** итоговое решение — `reject` (правило пробега не сработало, решение определяет LTV).

### AC-MILEAGE-08 — отсутствующее поле mileage: поведение не меняется до решения риск-менеджера

Ссылка: REQ-MILEAGE-02 (поведение при «неизвестном» пробеге на границе валидации и решения).

- **Given** payload без поля `mileage` (отсутствует или `null`).
- **When** вызывается `AssessmentService::assess()`.
- **Then** поведение валидации не меняется до решения риск-менеджера (см. OQ-MILEAGE-01): бросается `ValidationException` с ключом ошибки `mileage` (текущее поведение `ApplicationValidator.php:43`: `(int)null → -1`, валидация не пройдена, HTTP 422). `DecisionEngine` не вызывается, итоговое решение не выдаётся.

### AC-MILEAGE-09 — пустая строка mileage: поведение не меняется до решения риск-менеджера

Ссылка: REQ-MILEAGE-02 (поведение при «неизвестном» пробеге).

- **Given** payload с `mileage = ''` (пустая строка) и LTV ниже `ltv.approve_max`.
- **When** вызывается `AssessmentService::assess()`.
- **Then** поведение валидации не меняется до решения риск-менеджера (см. OQ-MILEAGE-01): валидация проходит (текущее поведение `ApplicationValidator.php:43`: `(int)'' → 0`, 0 ≤ `max_mileage_km`), `assess()` возвращает результат с `decision = approve` (пробег 0 ≤ 400 000, правило пробега не срабатывает).
