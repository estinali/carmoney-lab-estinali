**Задача (исходная формулировка):** добавить в расчёт решения по заявке проверку — пробег авто не больше 400 000 км, иначе решение review.

Перед вопросами агент сверился с `docs/setup/code_map.md` и `docs/plan/plan_MILEAGE.md`.

## Вопросы и ответы

**1. При mileage ровно 400 000 км (LTV при этом дал бы approve) какое решение возвращаем?**
Варианты: «approve (≤, включительно)» — mileage ≤ 400000 → approve, > 400000 → review; «review (<, исключительно)» — граница уже уходит в review.
**Ответ:** approve (≤, включительно).

**2. Если mileage заявки > 400000 и LTV одновременно > 85 (триггер на reject) — какое решение побеждает?**
Варианты: «reject побеждает» — LTV > 85 → reject, пробег не трогает; «mileage понижает до review» — пробег перебивает reject.
**Ответ:** reject побеждает.

**3. Что делаем с пустым/неуказанным пробегом?**
Варианты: ужесточить валидатор (отсутствие поля и `''` → 422); оставить как есть (`''` → 0 км, проходит); нет пробега → review без 422.
**Ответ:** не знаю, это к риск-менеджеру / владельцу продукта.

**4. Что помимо уже перечисленного в плане явно вне scope?**
Варианты: подтвердить scope из плана (не меняем: максимальный пробег 500 000 и текст ошибки валидации, саму валидацию, расчёт LTV, хранение, БД, frontend, seed, расчёт лимита и лимит LTV по возрасту авто, feature-тесты, UI на review); добавить в scope ужесточение валидации пустого пробега.
**Ответ:** подтвердить scope из плана.

**5. Имя ключа порога в rules.php?**
**Ответ:** max_mileage_for_approve_km. *(Решение реализации — для plan, в intent не входит.)*

**6. Где положить порог в rules.php?**
**Ответ:** секция vehicle. *(Решение реализации — для plan, в intent не входит.)*
